Server-side: nothing new — every endpoint needed already exists and is merged on `main` (G-Eskayo/marvin PR #370, plus the pre-existing `GET /boards/ticket` and `POST /boards/ticket/reply` from ticket #156/ADR 0037). This ticket is 100% client.
- **This is a redispatch, and I found the previous attempt's real bug.** This same ticket was run once already on this branch; its WIP survives at `refs/rescue/pipeline/g-eskayo/marvin-mobile#2/20261025T203705816454Z` (commit `a8f1990`, "WIP preserved before redispatch") after "mixed" verdict, 3 failed iterations. I read that WIP's design doc and diff and verified every data-shape claim against the real backend source (read via a sibling pipeline worktree that has the marvin repo checked out, `pipeline-g-eskayo-marvin-30`, cross-checked against `gh pr diff 370 --repo G-Eskayo/marvin`). Its research was almost entirely correct (board `label` vs README's stale `title`; `relations.forTicket`'s real `{tickets,prs,docs}` shape vs the README's wrong `{state,title,...}`). **But its `replyToTicket` sent `repo` and `number` as URL query parameters** (`Packages/MarvinCore/Sources/MarvinCore/BackendClient.swift` WIP diff: `url.append(queryItems: [...repo, ...number])`) **while the real route (`dashboard/mobile-backend/actions_api.js:17-54`) reads `repo`/`number` only from the parsed JSON body** (`const { repo, number, body: commentBody, confirmed } = payload`) and never looks at `req.url`'s query string at all. On a real device this call would post with `repo: undefined, number: undefined` — the one interactive, Face-ID-gated feature the ticket exists to deliver would silently fail against the real backend while its own self-authored unit tests (testing the same wrong assumption) still passed. This is the most likely cause of the failed verification, and this plan fixes it: `repo`, `number`, `body`, `confirmed` all go in the JSON body, matching `dashboard/mobile-backend/README.md`'s documented contract exactly.
- **A second, better-grounded correction:** the previous WIP never fetched the ticket's body/comments at all (no endpoint was in its `BackendClient` method list), so "plain-text body" in its `TicketDetailView` had no real data source. The actual fix is `GET /boards/ticket?repo=&number=` (`dashboard/mobile-backend/dashboard_api.js:71-90`, pre-existing from ticket #156) → `{number,title,body,labels,url,state,comments}` straight from `gh issue view --json ...`. This is exactly what the desktop's `ProjectBoard.jsx`'s `TicketDrilldown` calls (`window.api.boards.ticket`, line 246-248) — same endpoint, same shape, no new backend work, and it also supplies `comments`, closing a gap I'd otherwise have had to flag as missing.
- **Simplest sufficient approach, and one deliberate scope cut beyond the prior attempt:** no markdown/linkify renderer for the ticket body (plain `Text`) — same call the prior WIP made, for the same reason (real complexity, no second consumer). Given that, `/relations/context` (`relationsContext`/`ProjectContext`) has **no consumer** in this design — it exists only to feed `Markdown`'s linkify `ctx` on desktop. The prior WIP built it anyway (dead code against its own stated plain-text decision); this plan drops it. Same reasoning drops the desktop's `HumanTaskPanel` (ready-for-human "what you need to do" checklist) — not named in Gil's Scope-update list, desktop-specific, no second consumer. One column at a time via `TabView(.page)` doubling as the segmented picker (literally satisfies "swipe or segmented", no second control — per [[feedback-one-control-per-drilldown-level]]); dormant/archived boards shown inline-dimmed, not a second `<select>`-style control, same reasoning.
- **Where it spends vs. saves:** no model tokens (pure Swift/SwiftUI). It spends build complexity on lifting tab selection into `AppModel` (reused immediately when MR Review (#3) is built for real) and on getting the POST contract byte-exact this time. It saves a second failed pipeline run's worth of tokens by fixing the one thing that was actually wrong rather than re-deriving the (mostly correct) research from scratch.
- **More capable, not more passive:** Gil can browse every project's board, read a ticket's real history, labels, body and comments, and answer a waiting ticket from his phone — PRD #152 stories 30-36 — instead of needing a laptop.
- **Ticket's own stated fit:** none stated; nothing to correct there (the correction is against the *previous attempt*, not the ticket).
- **Explicit, stated gap:** ticket comments ARE available now (`/boards/ticket`'s `comments` field) — shown, last 5, like desktop. Nothing is silently dropped except the two named simplifications above (markdown/linkify, HumanTaskPanel), which are stated plainly here and in the closing comment, not discovered later.

## Tests to write first

All in `Packages/MarvinCore/Tests/MarvinCoreTests/`, following `BackendClientTests.swift`'s existing `StubProtocol` boundary-fake pattern (`Packages/MarvinCore/Tests/MarvinCoreTests/BackendClientTests.swift:7-39`).

**`planReply` (ports `dashboard/src/lib/ticket_input.js`'s `planInput`, verified against its actual source)**
1. `state != "OPEN"` → `requeue:false`, effect "This ticket is closed...".
2. `needs-reengagement` → `requeue:false`, "already queued to be rebuilt" effect.
3. `ready-for-human` or `wontfix` → `requeue:false`, "stays with you" effect.
4. `needs-info` → `requeue:true`, add `ready-for-agent`, remove `needs-info` + all `claimed:*`, "back to ready" effect.
5. A `claimed:*` label with no `ready-for-agent` → `requeue:true`, "parked after repeated failures" effect.
6. A `claimed:*` label **with** `ready-for-agent` already present → falls through to default (claim alone isn't enough once ready).
7. Precedence: closed wins over every label; `needs-reengagement`/`ready-for-human`/`wontfix` checked before `needs-info`; `needs-info` checked before a stale claim — exact `if`-chain order from the real source.
8. No labels, default state → default "agent reads the comments" effect, `requeue:false`.

**`BackendClient` new methods — against the *verified real* contracts, not README prose**
9. `boardDetail(repo:)` decodes `GET /boards/load?repo=` into `BoardDetail{repo,columns,otherProjects,fetchedAt}`; column decodes `label` (not `title` — README is stale, `board.js`'s real `COLUMNS` constant uses `label`).

12. `ticketDetail(repo:number:)` decodes `GET /boards/ticket?repo=&number=` → `{number,title,body,labels,url,state,comments}`, `gh`-shaped `labels:[{name,...}]` and `comments:[{body,author:{login},createdAt,...}]`.

23. Malformed/huge JSON (truncated body, a huge `columns` array) decodes-or-throws cleanly at the `JSONDecoder` boundary, never crashes.
